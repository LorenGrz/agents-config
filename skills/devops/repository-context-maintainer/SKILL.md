# Repository Context Maintainer

## Objective

Keep one concise, repo-local context file that helps agents understand the project before editing code. The default file is `.agents/CONTEXT.md`.

## Workflow

1. Check whether `.agents/CONTEXT.md` exists. If it does, read it before making architecture or implementation decisions, and use it to choose relevant skills.
2. Verify that it still matches the repository: current manifests, source layout, scripts, recent conventions. The context file is never more authoritative than current code.
3. If it is missing or stale, create or update it from the actual project, as a small preparatory change before larger implementation work. If the task is urgent and a refresh is not necessary, read the file and continue without rewriting it.

### Staleness signals

Refresh `.agents/CONTEXT.md` when any of these are true:

- The file is missing.
- The package manager, framework, or primary scripts changed.
- Source directories no longer match the documented architecture.
- The documented test/build commands fail because the commands no longer exist.
- New apps, packages, modules, or services were added.
- The user says the context is outdated.

### Context discovery

Use non-destructive inspection commands before writing:

```bash
pwd
find . -maxdepth 3 -type f \( -name package.json -o -name pnpm-lock.yaml -o -name package-lock.json -o -name tsconfig.json -o -name nest-cli.json -o -name 'next.config.*' -o -name app.json -o -name 'app.config.*' -o -name docker-compose.yml -o -name compose.yaml -o -name pyproject.toml -o -name requirements.txt -o -name pom.xml -o -name 'build.gradle*' \)
find . -maxdepth 3 -type d \( -name src -o -name app -o -name pages -o -name packages -o -name apps \)
rg -n "\"scripts\"|next|nestjs|react-native|expo|typeorm|prisma|vitest|jest|playwright" -g package.json
```

### File shape

If the file already exists (for example generated by `project-init`, whose template has its own sections, a 60-line cap and a `Last validated:` line), keep its sections and update them in place. When creating one from scratch, use:

```markdown
# Repository Context

## Purpose

## Stack

## Project Structure

## Package Manager And Scripts

## Architecture Rules

## Testing And Verification

## Local Development Services

## Agent Notes

## Last Reviewed
```

## Rules

- Keep the file concise and factual; prefer bullets over long explanations.
- Record only information discovered from the repository or explicitly provided by the user. Mark uncertainty as `Unknown` instead of guessing.
- Include exact commands for install, dev, test, lint, typecheck, build, and Docker only when they exist.
- Update `Last Reviewed` (or the file's own equivalent) with the current date and a short note about what was inspected.
- Do not include secrets, credentials, tokens, private keys, or machine-specific absolute paths.
- If multiple repositories exist, each repository owns its own `.agents/CONTEXT.md`.
